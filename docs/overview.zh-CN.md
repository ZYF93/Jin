# 概览：优势、局限与 Jin 的差异

Jin 是一个桌面 coding agent，最关键的设计选择是**架构优先（architecture-first）**：在写任何代码之前，它先产出一份可审阅的*架构变更提案*，等批准后才动手。本文说明这能给你带来什么、哪里不适用，以及它相对 Codex / OpenCode / Claude Code 的不同。

## 核心流程

```
扫描代码库 → 建立架构账本（L0 模块 / L1 文件 / facet）
   ↓
你提出需求 → 模型产出架构变更提案
   ↓
【人审阅并批准提案】   ← 关键闸门
   ↓
只允许在批准的文件白名单内实现
   ↓
自动 test / typecheck / lint → 失败回灌自修一轮
   ↓
架构一致性校验 + 一个带 Git checkpoint 的 WAL 版本
```

闸门之后的一切都**有边界、可验证**；闸门之前的都是**意图**——这正是你真正需要审的东西。

## 架构优先给你带来什么

- **你审的是意图，不是代码。** 提案说清动哪些 L1 模块/符号、影响面、以及自然语言的验收标准。对负责人/架构师来说，判断"加 `resetAll`、影响 a.ts/b.ts 对不对"比读 800 行 diff 快得多。
- **不会越界漂移。** 每个编辑都必须落在批准过的路径里；模型"顺手"想加个 helper 文件，会被工具层直接拒绝。
- **上下文被收窄到符号级。** 实现时只拉相关 LSP 符号（前后约 40 行）加目标文件的既有诊断，而不是整仓。token 更省，误伤更少，还顺带修已知问题。
- **正确性自动检查。** 写完后跑项目自己的 test / typecheck / lint，失败回灌自修一轮，再重扫确认批准的架构真的落成。
- **可逆。** 每轮是一个带 Git checkpoint 的 WAL 版本；一键撤销、不动 `HEAD`。

## 它和别家怎么比

| | 核心思路 | 强项 | Jin 的不同 |
| --- | --- | --- | --- |
| **Codex** | 沙箱执行 + 审批策略 | 安全沙箱、网络策略、稳定补丁 | Codex 拦的是*工具执行*；Jin 先拦*意图*，再把编辑限制在批准范围内 |
| **OpenCode** | 广 provider、全工具、会话管理 | 功能广：glob/grep/todo/webfetch/诊断、share/undo/compact | OpenCode 给模型更多工具；Jin 给更少更窄的输入 + 前置意图闸门 |
| **Claude Code** | 强模型 + hooks/子代理 | 长上下文 agentic、可扩展 | 同样是"先写代码"；Jin 多了架构闸门 + 内置验证/自修循环 |
| **Jin** | **架构闸门优先** | 可审的变更、受限编辑、自修、版本化撤销 | 验收前移到意图层 |

一句话：Codex/OpenCode/Claude Code 回答的是*"它能不能干成这件事？"*；Jin 回答的是*"我敢不敢让它在真实生产代码里自主改？"*——办法是把验收前移到动手之前。

## Jin 不适合的场景

- **一次性脚本、demo、快速原型**：账本 + 提案的开销不划算，直接用普通 coding agent 更快。
- **你压根不想审提案**：那核心价值就没了，闸门本身就是它的卖点。
- **特别乱的旧单体仓库**：架构账本好不好用取决于扫描质量；如果 L0/L1 边界分得不对，先审扫描结果。
- **你愿意为关心的语言装本地 LSP**：没有 LSP 时符号级上下文和诊断会缩水（扫描本身仍可用）。

## 设计取向，简要说

- **该确定的地方一定确定。** 账本、白名单、一致性校验，让"它到底按批准的做了吗？"是可回答的，不是凭感觉。
- **模型是被约束的工具，不是放开的行为体。** 它能在范围内读、暂存编辑、跑检查，但不能改写整个世界。
- **信循环，不信一次。** 写码只是其中一步；检查 + 自修 + 一致性校验才是让改动可信的部分。
