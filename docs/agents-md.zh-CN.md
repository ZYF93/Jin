# Jin 中的 AGENTS.md 规则

Jin 读取两层规则文件，并注入到每一个 LLM 步骤——语义扫描、规划器、每个实现 worker。项目约定、代码风格、输出语言因此能落实到**生成的意图**上，而不只是最终代码。

## 两层规则

| 层 | 位置 | 归属 | 编辑入口 |
| --- | --- | --- | --- |
| **项目规则** | `<项目根目录>/AGENTS.md` | 仓库（建议提交） | 任意编辑器 |
| **全局规则** | `<应用数据目录>/AGENTS.md` | 个人（按机器） | **设置 → Agent rules · AGENTS.md** |

两层都在每次调用时实时读取——改完文件，下一次扫描 / 规划 / 实现立即生效，无需重启 Jin。

每层每次注入最多 16,000 字符，超长的规则文件会被截断并附标记，避免规则把每个请求撑爆。

## 规则注入在哪里

1. **语义扫描精炼**。首次扫描（以及每次手动重扫）会跑一个 LLM 步骤，精炼架构元数据：文件/模块职责、kind 分类、领域标签，以及 **facet 级（方法/字段/属性）职责**。你的规则会拼进这一步的系统提示词，所以"永远使用中文回复"会让审阅对话框里出现中文职责描述。
2. **规划**。规划器收到规则后，任务拆分、验收标准、节点意图都必须在规则约束内生成。
3. **实现**。实现代理的系统提示词携带规则；每个子代理还会额外收到一段显要的 "Facet-level intent (must satisfy)" 块，列出其文件范围内已批准的意图，并要求完成前逐条自检。

扫描期生成的 facet 意图会对照 LSP/结构事实校验：模型编造的、代码里不存在的成员名会被直接丢弃，不会进入架构。

## 示例

```markdown
# 项目规则

- 永远使用中文回复（包括架构节点职责、意图描述）。
- 组件放在 src/features/<domain> 下，禁止跨 domain 引用内部实现。
- 数据访问一律通过 repository 层，组件不得直接查询数据库。
- 每个新函数都要有 JSDoc；导出函数必须有单元测试。
- 提交信息使用 Conventional Commits。
```

把个人通用偏好（语言、回复风格）放在**全局**文件，把仓库相关的约定放在**项目**文件，这样项目文件对协作者同样有用。

## 规则能做什么、不能做什么

- ✅ 输出语言、命名、代码风格、分层约束、测试期望、回复语气。
- ✅ 模型在写职责与意图时应遵守的领域知识。
- ⛔ 不能扩大文件白名单——写路径由批准的架构强制约束，不靠提示词。
- ⛔ 不能绕过审批闸门：实现仍然等待你的审阅批准。

另见 [概览](overview.zh-CN.md) 了解闸门机制，[快速上手](getting-started.zh-CN.md) 完成第一个被批准的变更。
